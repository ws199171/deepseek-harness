# Agent Note: 编排哨兵

Status: implemented

[English](2026-10-04-orchestration-sentinel.md) | 中文

## Problem

模型每一步只发出一个并发安全的工具调用时，会为每次调用都付一个往返——即便这些调用互不依赖，而内核本可以在一条消息里并行执行它们。模型反复调用同一个工具时（例如逐个文件 `read`），每个条目付一次调用，而一小段程序就能完成。

常驻指令并不合适。系统提示里的散文（"把互不依赖的调用合批"、"重复时优先 `run_code`"）会在一个部署的每个会话的每次请求上花 token，无论模式是否出现，而且它无法对模型**实际在做的事**作出反应。更糟的是，会变化的系统提示段落会替换提示的第一个表层节点、使可缓存前缀失效，因此一条以省 token 为目标的提醒反而得先为重建缓存付账。

## Decision

`@deepseek-ai/dsh-orchestration-sentinel`（`packages/guard/orchestration-sentinel`）贡献**一个**动态运行时上下文，且只在日志显示该模式时贡献。它是建议性的：绝不阻塞、绝不重写调用，也不对已经执行过的调用做任何断言。

### 决策运行的位置

在本贡献自己的 text provider 内部，而不是 `agent/pre-step` 监听器里。内核**先**装配提示、把动态上下文落库，**之后**才 dispatch pre-step waterfall（`packages/core/agent-loop/src/agent.ts` 的 `preStep`），因此在监听器里决策会晚一步才可见。在装配期决策能把提醒放进模型即将写入的那一步——那是它唯一还能影响的步骤。provider 读到的窗口只含已完成的步骤，而这正是两个机制需要的证据。

### 两个机制

**合批提醒**在末尾 `singleCallStreak` 步各恰好发出一个调用、且这些调用经工具注册表判定全部并发安全时触发。某一步发出两个及以上调用会在折叠状态里打断这一连击，因此模型一旦合规提醒就自动沉默，不需要单独的反馈通路。

**`run_code` 建议**在末尾 `windowSteps` 步内某个工具出现次数达到 `repeatedToolCalls`、每次出现都并发安全、且该 agent 能看到 `run_code` 时触发。可见性是让建议可执行的闸门：在工具呈现模式隐藏了 PTC 传输的部署里 `run_code` 无法被调用，该部署也因此不发这条建议。

两段文案都是被观测窗口的纯函数，窗口里包含轮次与覆盖的步区间，因此相同的观测产生相同的文本。

### 状态

一个 `ctx.sessionProjections` 单元就是本插件持久状态的全部。它把 `tool/call` 事件折叠成按轮次的步缓冲，并把插件自己发出的快照折回以计数发射。因此插件不持有权威状态：恢复或分叉的会话通过重放日志重建同样的窗口与同样的预算，而审计工具按同样规则数快照会得到与插件相同的数字。被压缩移除后重新物化的快照重复同一文本，不会被计两次。

### 对循环卫生守卫的让位

`repeat-tool-reminder` 报告的是"同一工具、完全相同的参数"的循环。这种情形同时满足 `run_code` 机制的形状，而用"把它变成程序"来回答会把循环固化、而不是缩短它。在该轮次的剩余时间里插件不发 `run_code` 建议；合批提醒不受影响，因为它回答的是另一个问题。该判定只从日志里读一个来源名，因此无论那个守卫是否被加载都成立。

### 配置与组合

`enabled`、`observeOnly`、`windowSteps`、`singleCallStreak`、`repeatedToolCalls`、`cooldownSteps`、`maxEmissions`、`enableSplit`、`enablePtcSuggestion`；`windowSteps` 与 `singleCallStreak` 上限为 8，固定 16 步的折叠缓冲足以覆盖。本包不在任何 bundle 里：部署方用自己的补丁行选择加入，因此默认组合不变。

## Alternatives considered

- **`tools/post-execute` + `PostToolDecision.additionalContexts`** —— 同族循环卫生守卫用的通道，带 `notice` 形式的来源，且能精确归属到触发它的那次调用。因**时序**被否决：post-execute 运行时当前步仍在进行，调用集合尚未确定，提醒会落在模型已经选好下一步动作之后。它还会失去"被压缩移除的快照自行回来"这一性质。
- **在 `agent/pre-step` 监听器里决策** —— 最初的实现。由活动循环测试发现提醒晚一步到达后否决，晚一步就错过了它存在要影响的时刻。
- **常驻的 `systemPrompt.section()` 规则** —— 否决：无条件请求成本，且会变化的系统段落会替换第一个表层节点、使可缓存前缀失效。
- **推断跨步依赖** —— 否决：不可观测。因此两段文案都保持条件式，不点名任何具体调用"可合并"。
- **把窗口放在插件侧的 map 而不是投影单元里** —— 否决：会话发射预算会在恢复时归零，声明的每会话上限就不成立，且重启后没有任何东西能重建窗口。
- **用内存计数器统计发射** —— 否决：计数必须能从日志推导，因为日志必须解释模型看到的一切。

## Consequences

买到：在模式真正出现之前零请求成本；模型看到的每一个字都在日志里、每次发射都可从日志审计；决策对重启与分叉稳定；合规会自动让提醒沉默；`observeOnly` 能在注入任何东西之前度量可干预窗口是否常见。

代价：第一次发射在构造上就是晚的——必须先走完一段步才能形成模式。并发性按工具名、以空参数判定——对仓库内每个工具都精确（它们要么是 `() => true`，要么未声明分类器），但对依赖参数的第三方分类器偏乐观；由于两段文案都是条件式建议，这份乐观只会让提醒时机偏差，不会对已执行调用产生误导。系统提示上下文之间没有优先级机制，因此同时运行另一个提供常驻合批指令插件的部署会为两段文本都付费。分发是手动的：本包不在任何 bundle 里。

## Testing

`tests/sentinel.spec.ts` 用脚本化适配器驱动真实 agent loop，并断言记录在会话日志里的引导；`tests/loader-composition.spec.ts` 通过真实 Loader 读取 test-only `cordis.yml` 激活插件，并断言装配出的模型可见快照；`tests/context.spec.ts` 覆盖活动循环够不到的贡献契约；`tests/{config,state,guidance,decide}.spec.ts` 覆盖 schema、折叠、文案与决策。`src/**` 的逐文件覆盖率为 100%。

## Deferred

- 该场景的 keyless recorded-session 快照需要由 owner 录制一次。
- 只有当部署打开它时才会注入：观测模式的存在，是为了在任何引导到达模型之前，先按预先注册的 kill criteria 度量可干预窗口。
- 该行是否加入某个 bundle、以及是否默认启用，都等同一批证据。

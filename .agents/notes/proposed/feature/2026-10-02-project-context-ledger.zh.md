# Agent Note: 项目上下文账本 —— 作为独立 DSH 插件的持久项目上下文

Status: proposed

[English](2026-10-02-project-context-ledger.md) | 中文

## 问题

DeepSeek Harness 解析的是*工作区*，不是*项目*。当会话在某个目录中启动时，模型无从得知这是哪个项目、该项目已经做出过哪些决定，以及上一个会话留下了什么。由此产生三个后果：每个新会话都要从零重建同一套心智模型；项目级决定只存在于对话历史中，第一次压缩就会消失；而超出窗口的长任务无法在任何地方继续。

现有的一等公民包只覆盖了其中一部分，仅此而已。`dsh-agent-instructions` 会加载 `AGENTS.md`/`CLAUDE.md` 指引，但不保存记忆、不保留归档、也不执行交接。`docs/cookbook/extension-cookbook.md` 把 Memory 定义为一行配方——"section provider + tool"——其背后没有实现。`dsh-session-reference` 能够为另一个会话建立快照，但没有任何东西把它变成接续能力。

有两个社区插件占用了最直观的名字，且都不可用。`buhuikongpan/dsh-project-context` 只注入一段固定文字，宣告该目录是一个项目；它没有记忆、归档或交接。`P02-1010751281/dsh-project-context` 宣称的正是缺失的功能集——带机械索引的会话归档、记忆整合、自动交接——但在 dsh 0.1.7-rc.2（`boot failed`）和 0.1.7-alpha.2（插件目录树加载失败）上均未通过 L5 运行验证，因此不存在可用于改进的可用基线。它还把记忆写入 `CONTEXT.md` 与 `MEMORY.md` 并以其为真相源，这绕开了会话日志，违反了 *Model-visible ⟺ logged*。

四种失败模式已被刻画清楚：压缩丢弃注入的约束、跨 agent 的上下文碎片化导致集体策略违规、被污染的上下文导致注意力稀释，以及窗口硬溢出。DSH 的架构优势在于上下文处理可以被审计和替换；目前没有任何插件在项目这个尺度上运用这一优势。

有两项约束统摄整个设计，而不只作用于某一层。

**新上下文消耗的不得多于它节省的。** 一个把项目知识带入每个会话的插件，如果"带入"这件事本身吃掉了使任务得以完成的预算，它就毫无价值。在这里，克制是功能需求，不是调参练习。

**第三方插件不能向会话日志追加内容。** 读取方只有在信封携带 `ignorable: true` 时才接受未知的存储事件，而 `Session.append()` 无法设置该标记；因此追加了新事件类型的插件会留下一个连它自己的读取方都拒绝的日志。本设计记录的每一项持久内容因此都存放在日志之外，而模型看到的一切都由那些本身就会记录日志的扩展点承载。

## 提案

新增 **`dsh-context-ledger`**，一个安装进 profile bundle 的独立 DSH 插件。它无需改动 DSH 源码。它让会话获得一个持久、可审计的*项目*概念：这是哪个项目、它携带哪些约定、已经学到了什么、上一个会话得出了什么结论，以及还剩多少上下文预算。

该插件由六层组成，每层只建立在有文档记载的扩展点之上。

激活是部署级的，通过一个经过校验的 `enabled` 字段控制。只有携带 `cwd` 的会话参与；系统会话与后台会话不受影响。不提供按会话的开关，因为持久地记录一个开关需要插件自有的会话事件（见"没有插件自有的会话事件"）。

有三条原则贯穿每一层：

**仅限本地。** 插件不在项目目录树内写入任何内容。记忆存放在 `$DSH_HOME` 下，以解析出的项目根为键，且永不进入版本控制。一个项目的记忆属于一台机器上的一个用户。

**不赚取则不携带。** 项目作用域的知识会被注入到该项目的每个会话，因此它的大小是对未来每一次会话的长期征税。只有经过确认、且足够简短的条目才能赢得永久注入的位置。

**两个作用域，两种生命周期。** 项目作用域跨越会话存续且受严格约束；会话作用域随其会话终止，且永不被重新注入。

### 层级映射

| 层 | 职责 | DSH 扩展点 | 已构建 |
|---|---|---|---|
| 1 身份 | 项目根、技术栈行、记忆索引 | `ctx.systemPrompt.context()` | 是 |
| 2 约定 | 目录级 `CONTEXT.md`、渐进式披露 | `tools/result` 触碰追踪、`agent.inject()` | 是 |
| 3 记忆 | 记录、读取、检索、确认、本地持久化 | `ctx.tools.register()`、`$DSH_HOME` 下的文件 | 是 |
| 4 接续 | 机械会话归档、交接简报 | `ctx.sessions` flush、`ctx.sessionQuery`、插件自有文件 | 部分 |
| 5 模型可见面 | 账本对一次请求贡献什么 | 运行时上下文快照；约定走 inbox 注入 | 是 |
| 6 预算 | 档位、上限、自适应级别、普查、会话用量 | `ctx.tokenMeter`、`ctx.llm`、解析出的预算 | 是 |

### 上下文作用域与生命周期

**项目作用域**是归属于项目、跨越任一单个会话而存续的知识：构建命令、归属边界、已经定下的决定、反复出现的坑。它通过第一层注入到该项目的每个会话。由于这种注入是无条件的，其规模受到双重上限——条目数硬上限与字节硬上限——且准入被限制为人工确认过的条目（见信任梯度）。失去位置的条目不会被删除，而是变为仅可检索，通过 `ledger_read` 与 `ledger_search`。

**会话作用域**是属于进行中工作的知识：当前子目标、正在检验的假设、中间发现。它尚未构建，而且目前没有可行机制。原本要用会话事件来记录它，而第三方插件无法创建事件类型；写入磁盘会与定义该作用域的非持久化规则相矛盾；而作为按请求注入的块则会因留在历史中而比它的会话活得更久。因此这一层是作为一个设计问题被推迟，而不是作为未写的代码；它对其上各层也不构成承重。

| | 项目作用域 | 会话作用域 |
|---|---|---|
| 跨越其会话存续 | 是 | **否** |
| 每请求注入 | 是，有上限 | 否——存在于该会话自身历史中 |
| 写入磁盘 | 是，位于 `$DSH_HOME` 下 | **否** |
| 新会话可见 | 是，若它占有位置 | **否** |
| 准入需经确认 | 是 | 否 |
| 被移除后的行为 | 退化为仅可检索 | 视为从未记录 |

会话作用域明确不是暂存区：一个条目不会因为有用就毕业到项目作用域，因为"有用"没有机械判据。晋升是一次单独的、带已记录批准者的动作，这正是让永久注入载荷处于人工控制之下的机制。

### 第一层 —— 项目身份

插件从会话 `cwd` 向上查找并匹配 `projectRootMarkers`（默认 `['.git']`）来解析项目根。标记是目录还是文件都算，因此 worktree 或 submodule 的根也能被找到。与一等公民加载器的同类查找不同，标记未命中会被如实报告而不是被抹去：一个光秃秃的目录不是项目，插件什么也不贡献，而不是断言一个它并不具备的身份。

通过 `ctx.systemPrompt.context()` 注册一个名为 `context-ledger:identity` 的动态上下文，位置在 `SANDBOX_POLICY` 之前。该 provider 在每次装配时重新求值，输出项目名、项目根、存在的清单，以及赢得了位置的记忆标题行。由于装配出的快照声明其取代更早的运行时上下文快照，分支切换或新确认的事实都会在下一步可见，无需显式失效。

这个块被刻意做得小，也被刻意做得稳定。渲染是其输入的确定性函数——固定字段顺序、LF 换行、无时间戳、无本地化格式——因此当输入未变时，相邻步骤会输出逐字节相同的文本。不稳定的前缀文本会使每个请求的 prompt cache 失效，其代价远高于这个块本身；同类缺陷在工具枚举顺序上已有记载。因此，确定性排序是约定的一部分，而不是实现细节。

缓存以**渲染出的文本**为键，而不是输入的摘要。摘要是文本的代理，而代理可能漏掉某个输入并交出陈旧的块；直接比较文本则不可能出现这种分歧。

### 第二层 —— 约定

已构建。这一层不会重新实现指令加载：`dsh-agent-instructions` 已经拥有 `AGENTS.md`/`CLAUDE.md` 的发现、baseline 加 `.local` 覆盖的解析、按目录去重、触碰时刷新，以及持久的 user-role 注入；重复其中任何一项都会让同一个事实产生两个归属方。

账本新增的是一类该包刻意不占用的事实文件：目录级 `CONTEXT.md`。它们承载任务形态的项目知识——如何运行测试、正在迁移哪个模块——而不是行为指令。它们由人编写、从项目目录树中读取；插件永不写入它们。

投递遵循渐进式披露。`tools/result` 追踪一次成功的 `read`/`write`/`edit` 触碰了哪些路径，而被触碰的路径会通过从该文件自身目录向上走到项目根，解析出候选约定文件。因此最近的约定最先到达，而根级的那份仍然覆盖一切。候选在被读取之前就被标记为已投递，因此被反复触碰的目录只会被探测一次，且每个文件在每个会话中至多投递一次。

投递走 `agent.inject()`，而不是常开块。这正是让一个约定的成本成为一次性而非每请求的原因；而 inbox 是受认可的种子上下文通道：Harness 会把这次拼接记录为 `agent/inbox/spliced`，因此注入仍处于 *Model-visible ⟺ logged* 之内。

有两条界限。超过单文件上限的文件会作为一条说明投递而不是被丢弃——模型从未被告知的约定与不存在的约定无法区分——而会话的约定总字节数单独设限，因此一个到处都有 `CONTEXT.md` 的项目无法累积出无界的一次性成本。

投递的消息携带一个本插件自有的 source kind。`MessageSourceMap` 是刻意可合并扩展的：每个生产者声明自己的 kind，消费者对未知 kind 向下穿透。会话格式确认了这种开放性而非仅仅暗示——它的迁移链会把无法识别的插件标识映射为 `plugin:<name>` 而不是拒绝——因此既不需要注册，也不可能遮蔽任何一等公民 kind。

早先的草稿打算像 `dsh-agent-instructions` 那样，经由 `agent/pre-step` waterfall 加 inbox 拼接来投递。只用 inbox 就够了：本插件为下一步添加上下文，从不改写决策，因此那个 waterfall 连同它的 step-open 簿记，会是一套没有任何东西可决策的机器。

### 第三层 —— 记忆

记忆持久化在 `$DSH_HOME/context-ledger/` 下，以解析出的项目根及其路径哈希为键，并带一个可读的名称前缀，便于调试时辨认目录。项目目录树内不写入任何内容，因此没有任何东西可以被提交，用户也不需要维护 `.gitignore` 纪律。

每个条目一个 markdown 文件，带版本化的 JSON frontmatter 头。用 JSON 而非 YAML，是因为头部必须精确往返且解析不需要依赖；用 markdown，是因为正文是人预期要阅读和编辑的文字。写入先落到同目录的临时文件再改名就位，因此读取方不会观察到写了一半的条目，写入被中断也会保留先前的内容。

刻意没有派生索引文件。列表通过扫描目录完成，这为内容保住了单一真相源，并消除了"缓存与其来源不一致该怎么办"这个问题。条目 id 由其种类与规范化后的标题派生，因此重复记录同一个事实会原地更新它，而不是累积近似重复项。

写入经由面向模型的工具发生，绝不通过人的直接写文件；但文件仍然可编辑：不可读或格式错误的文件会被连原因一起报告并跳过，绝不会让一次列表或一个会话失败。

条目在重写时保留其层级。用新的措辞重写一条已确认事实不会静默地将其降级，因为那会让一次编辑的副作用撤销一个人做过的决定。

面向跨项目事实的全局作用域已规划但未构建；存储目前只有项目作用域。

### 第四层 —— 接续

归档已构建。每个在项目中运行过的会话在销毁时被归档，行仅从其会话日志推导——没有模型调用——因此它自身不会丢失信息，也不会与它所来自的日志产生分歧。一行记录跨度、轮次数、步数、工具调用数、压缩次数、目标变更次数、最后一轮如何结束，以及该会话触碰过的文件。

捕获是有序的而非顺带的。销毁发生在 driver 静默之后，因此内存中的日志是完整的，但带缓冲的事件可能尚未落盘；所以插件先 flush 再读取，因为先读取会归档一行悄悄漏掉尾部的事件。销毁是 emit 而非串行派发，因此没有东西等待捕获：它自己负责自己的失败，绝不会以拆除错误的形式浮现。项目从未被解析出来的会话不会被归档，因为没有账本可以把它归入。

预期设计有两部分被推迟，原因相同——可达的接缝不接受设计想交给它的东西。

**跨会话快照。** `ctx.sessionReferenceResolver.prepare()` 是构建另一个会话有界只读视图的受认可方式，且可从插件调用。但该服务不在随附 bundle 中，因此依赖它的简报在默认部署里会是一段死代码。它属于挂载了该服务的部署。

**自动开启接续。** 开启一个新会话并以简报作为种子并不可达：`ctx.subagents.startContinuable` 会创建新会话，但其种子来自 provider 而非调用方；而 `ctx.agents.create({ seed })` 是 agent-loop 工厂基础设施，不是已发布的插件接缝。子 agent 也是错误的形态——它是一项被委派的任务，而不是主线程的延续。

因此交接产出的是一份**简报**。它是归档行与注入事实的纯函数，受字节上限约束，并按固定顺序让位：先事实，因为在同一项目中启动的会话会自动收到它们，它们是目的地处唯一真正冗余的部分；然后是路径列表；然后是除最近一条之外的所有行；最后是除头部与收尾指令之外的一切。任何值都不会被中途截断。

简报的最后一行才是真正的指令，也是这一层的意义所在：在这个项目里开一个新会话，而不是继续一个快满的会话，因为新会话会自行拿到项目块与已确认事实，而简报只补充正在进行中的部分。

压缩次数来自折叠 `compaction/start` 事件，而不是投影。`CompactionEngine` 只暴露压缩操作，不暴露当前用量，而插件自有的投影单元需要 zod schema 与合并后的投影键。折叠计数所来自的那同一份日志可以避开这两者，也避开了依赖 `session-stats` 被挂载——它不在随附 bundle 中。

那次折叠读的是 `compaction/start` 与 `compaction/end` 这一对，于是产生一个问题：部署能否换入自己的压缩引擎，并悄悄停止发出它们。不能。这一对是**强制**的而非约定俗成的：压缩不变量会让一个没有匹配 `compaction/start` 的 `compact-checkpoint` 替换失败，而会话格式会拒绝没有 start 的 summary、或没有恰好一个 summary 的成功 end。一个两者都不发出的引擎会先在自己的检查上失败，因此归档的压缩计数依赖的是平台保证，而不是某个引擎的良好行为。

### 第五层 —— 模型可见面

账本放到模型面前的一切都经由本身就会记录日志的扩展点，因此 *Model-visible ⟺ logged* 无需插件自有的事件类型即可成立。

身份块是一个运行时上下文快照。`RuntimeContextProjection` 把它物化为一条持久的 user-role 消息，且仅在留存文本不同时才物化。这带来两个值得说明的后果：每一次实质变化的快照恰好是一条被记录的消息；而逐字节稳定不是锦上添花，而是阻止日志被重复内容填满的机制。

逐条目的簿记——正文、时间戳、层级变更史——完全不进入任何请求。只有一条有界的标题行会，且只针对人工确认过的条目。正文按需获取，因此其输出像其他工具一样受工具结果上限约束。

这一层取代了早先"为每个插件事件注册消息投影"的计划。该计划不可实现：投影解释的是事件类型，而第三方插件无法创建事件类型。

### 第六层 —— 预算与自省

`ledger_status` 报告解析出的预算档位及其上限、按种类与层级划分的普查、有多少条目录占有位置、有多少条仅可检索、有多少文件被跳过、注入块的字节大小，以及会话 token 用量及其推导依据。它自身不保存任何状态。

它是 Codex 的 `_context` 工具的对应物：让模型在预算压力演变为失败之前就能看到它，而不是在轮次被截断之后才发现。

会话用量来自 token meter 的 `measure(session)`，以及在路由可解析时模型声明的上下文窗口。压缩不暴露用量，因此窗口是独立地从所路由的模型解析出来的。一条无法解析的路由只会让窗口这一项缺失，而不会让整份报告失败。

### 预算档位

`budgetProfile` 选择一组具名的上限集合，插件在任何约束生效之前先把该请求解析为一个具体的 `BudgetSpec`：

```ts
resolveBudget(request?: {
  profile?: 'frugal' | 'balanced' | 'full'
  overrides?: Partial<BudgetCeilings>
}): BudgetSpec
```

`resolveBudget` 是归属实现中的一个显式步骤，而不是藏在注入路径里的默认值，因此实际生效的数字可通过 `ledger_status` 检查，并可在重放中复现。各上限仍可单独覆盖；档位是起点，不是锁。

| 上限 | `frugal` | `balanced`（默认） | `full` |
|---|---|---|---|
| `maxIdentityBytes`（整块） | 512 | 2048 | 8192 |
| `maxIndexEntries` | 4 | 16 | 48 |
| `maxIndexBytes`（仅标题行） | 512 | 2048 | 8192 |
| `maxIndexEntryBytes`（标题行上限） | 96 | 160 | 320 |
| `maxEntryBytes` | 4096 | 16384 | 65536 |
| `maxSearchResults` | 5 | 10 | 25 |
| `maxExcerptChars` | 120 | 240 | 480 |
| `maxArchiveRows` | 3 | 10 | 25 |
| `maxArchivedPaths` | 10 | 20 | 40 |
| `maxBriefBytes` | 2048 | 4096 | 8192 |
| `maxConventionFileBytes` | 4096 | 16384 | 65536 |
| `maxConventionSessionBytes` | 8192 | 32768 | 131072 |

零是一个可用的上限，意为"无"。自适应档位的地板正是用它表达"没有标题行"，部署也用它在不换档位的情况下关掉某一条路径。

**上限的单位是字节，不是 token。** token 计数的上限需要插件并不具备的分词器，而把字节数当作 token 数报告会虚报已知信息。字节上限精确且执行成本低。`ledger_status` 另行报告会话的真实 token 用量，并标明它是会话级数字，而非账本的份额——因为把一次测量到的会话总量的一部分归给单一贡献方，是现有接口并不支持的事。

`full` 抬高每一项上限并保留它们。它并没有移除上限：无上界的常开注入正是这套机制所要防范的失效，因此真正想要无上界的部署应通过覆盖显式声明，使其在配置评审中可见，而不是由一个名字听起来安全的预设来暗示。

档位只调节规模。没有任何档位会改变某个作用域的生命周期，或让未经确认的条目进入索引。那些是设计的不变量，不是设置项。

#### 自适应

`adaptive` 是动态模式，且已构建。它刻意不按请求计算大小：一个每一步都变化的载荷会使 prompt cache 失效，其代价高于它所承载的知识。

它改为从空闲窗口中选择一级：

```
rung = the widest profile whose maxIdentityBytes fits within
       (contextWindow - usedTokens) * adaptiveUtilizationRatio
```

阶梯就是上面三个档位，外加 `frugal` 之下的一层地板——在那一级账本只贡献身份块与目录行。对于一个几乎耗尽的窗口，那层地板才是诚实的答案：正确的行为是停止添加，而不是继续保留一条标题行。它不是可选的档位，因为部署不该能直接要求它、然后纳闷为什么自己的记忆是空的。

级别只在检查点选择：会话开始、轮次边界，以及一次压缩结束。在检查点之间块是逐字节稳定的，因此第一层的缓存属性成立。压缩检查点与归档的压缩计数享有同一个平台保证——那一对括号是强制的，因此替换引擎无法在窗口被填满的同时悄悄让级别不再被重新测量。当窗口无法测量时——没有 token meter、没有可路由的模型，或路由未声明窗口——插件使用默认档位而不是猜测，因为猜错要么是一个静默为空的账本，要么是一个静默超大的账本。

由于一个缩小的载荷与一个损坏的载荷无法区分，`ledger_status` 会报告配置的档位、当前级别、比例、其背后的测量，以及测量为何可得或不可得。在地板级别上它还会用文字说明，因为那正是运维最可能误认为故障的情形。

`adaptiveUtilizationRatio` 默认为 `0.05`。

#### 以发现取代淘汰

档位决定推什么。它们并不回答那些没被推的知识会怎样，而模型看不见的条目也不会被它惦记。有两种机制补上这一缺口，且两者都已构建。

**目录行。** 块始终报告记录了多少事实、其中多少赢得了标题行，并按种类细分——例如 `Memory: 12 recorded, 2 shown (build 4, decision 5, pitfall 3)`。它只在什么都没记录时才省略，因此一个所有事实都未确认的项目仍会表明它们存在。它报告的计数是**实际显示在屏幕上的**，而不是仅仅具备资格的：一条宣称了已被让位的标题行的目录行会误导模型对可见内容的判断。

**`ledger_search`。** 一个按关键词查询标题与正文并返回有界匹配的工具。这是结构性的修法：检索比注入更廉价，无须上限即可扩展，并让模型按任务所需去索取，而不是收到一堆它并未要求的标题行。

两者合起来改变了问题的形态。在只有上限的情况下，风险是模型永远不知道知识存在；有了目录行与检索工具，最坏情况是多一次工具调用，而上限从一个"模型被允许知道什么"的选择，变成一个关于成本的选择。

### 约束的放置

本笔记所依据的源设计提出了三档 immutable / high-priority / evictable 投影优先级，以在压缩面前保卫注入的约束，并援引"当前压缩器仅保留约 17% 的注入式侧约束"这一证据。在 DSH 中这场斗争是不必要的，账本通过放置而非优先级来避开它：

| 约束类别 | 存放位置 | 会被压缩丢失吗 |
|---|---|---|
| 系统、安全、合规 | `ctx.systemPrompt.section()` | 否——每次请求重新渲染，从不物化为历史 |
| 任务级：当前目标、活跃约束 | `ctx.systemPrompt.context()` | 会随历史被压缩，随后被重新发出：投影在被移除的同一刻就忘掉该快照 |
| 项目身份与记忆索引 | `ctx.systemPrompt.context()` | 同上 |
| 对话历史 | 会话日志投影 | 是 |

精确的说法很重要，而且现在是**已验证**而非仅仅断言。运行时上下文快照*确实*是一条持久的 user-role 消息，因此*确实*位于可压缩区域之内；本笔记的早先草稿说的是相反的话，已被更正。取代它的说法提出了一个更尖锐的担忧：投影只在其文本与它所留存的不同时才发出，因此一个被压缩掉、而投影仍以为它被留存的快照，会让块**永久消失**。

这不可能发生，其原因是一条不变量，而不是巧合。只要某个替换表层事件在其 `sourceEventSeqs` 里引用了该快照的 seq，投影就会使其留存的快照失效（`packages/core/agent-loop/src/runtime-context.ts:134-142`）。而会话表层拒绝移除任何未被列进替换事件 `sourceEventSeqs` 的节点（`packages/core/session/src/surface.ts:367-370`）。所以"快照被压缩掉了"与"投影忘了它"是**同一个条件**，块会在下一次装配时被重新发出，无论其文本是否变化。

由此有两个后果。逐字节稳定仍然重要，但理由与早先草稿给出的不同：它防止的是"每步一条消息"，而不是永久丢失。而且存在的是一个有界的间隙而不是洞——`project()` 运行在压力压缩所在的 pre-step waterfall **之前**，因此压缩移除该快照的那一步会省略它，而下一次装配会把它恢复。溢出恢复同理，重试的那一次请求可能漏掉它。

任何绝不能丢失的内容，都不会被放在只能从历史里找回的位置。因此可压缩区域的保留由**重新发出**处理，而不是由压缩器内部的优先级方案处理；而放置方式正是让成本变得可预测的东西：对话之外的一切都以配置所控制的大小累积，而不是随对话长度累积。

### 没有插件自有的会话事件

早先的草稿规定了七个携带 `ignorable: true` 的 `ledger/*` 会话事件类型。第三方插件一个都无法实现，原因值得记录。

`Session.append()` 从 `type`、`seq`、`time`、`data` 加上 surface 元数据构建信封。`ignorable` 是信封字段，没有任何 append 参数能设置它。读取路径会拒绝任何不在生成式已知类型集合中的类型，除非该标记存在。一等公民包能进这个集合，是因为它们在仓库内；安装进 profile 的插件进不去。插件开发规范直接写明了规则：不要用新的类型追加会话事件；从已有事件推导状态，或把插件自有数据放进通过检查发现的存储中。

其后果，上文均已体现：

| 早先草稿存放在 | 现在存放在 |
|---|---|
| 按会话的启用开关 | 部署级的 `enabled` 字段 |
| 按会话的预算覆盖 | 部署级的 `budgetProfile` |
| 记忆的提议、提交、退役 | `$DSH_HOME` 下的文件，层级写在条目的头部 |
| 归档行 | 未构建；将是插件自有的文件 |
| 交接记录 | 未构建 |
| 那些事件的消息投影 | 没有可投影之物；块是一个运行时上下文快照 |

事件设计本想买到的性质——可重放的插件状态——确实丢失了，它被记为一条风险而不是被粉饰过去。没有丢失的是 *Model-visible ⟺ logged*，因为块由一等公民机制承载，而该机制会记录日志。

### 存储布局

```
$DSH_HOME/context-ledger/
  projects/<name>-<hash12>/
    memory/<entry-id>.md
```

项目目录树之下不写入任何内容。`<name>-<hash12>` 把一个可读的目录名与解析出的项目根的哈希配在一起，后者才是真正标识项目的东西：两个同名目录的检出不会冲突，而把检出移到新路径会开启一个不同的项目。条目 id 在被拼接到路径之前会按严格模式校验，因此模型提供的 id 无法寻址记忆目录之外的文件。

没有任何派生产物。条目文件就是内容，也是关于它的唯一权威。

### 配置

每一项随部署而变的取舍都是经过校验的 `Config` 字段，没有任何常量被硬编码。

| 字段 | 默认值 | 含义 | 已构建 |
|---|---|---|---|
| `enabled` | `true` | 是否贡献任何内容 | 是 |
| `archiveEnabled` | `true` | 会话销毁时是否归档 | 是 |
| `contextOrder` | `100` | 在运行时上下文中的位置，位于 `SANDBOX_POLICY`（110）之前 | 是 |
| `projectRootMarkers` | `['.git']` | 用于解析项目根的标记 | 是 |
| `stackManifestNames` | `['package.json']` | 在技术栈行上报告的清单 | 是 |
| `includeProjectName` | `true` | 是否包含项目名行 | 是 |
| `budgetProfile` | `'balanced'` | 具名上限集合 | 是 |
| `budgetOverrides` | `{}` | 在档位之上逐上限覆盖 | 是 |
| `ledgerHome` | `$DSH_HOME` | 账本根目录；其外不写入任何内容 | 是 |
| `conventionFileNames` | `['CONTEXT.md']` | 目录级约定文件；不得与指令文件候选重叠 | 是 |
| `adaptiveUtilizationRatio` | `0.05` | 自适应模式可用的空闲窗口比例 | 是 |

自包含的配置错误在加载时失败。非有限的 `contextOrder`、空的标记或清单列表、未知的预算档位、未知的覆盖键、不是非负整数的上限，以及非正的 `adaptiveUtilizationRatio`，都会让激活失败，而不是静默改变行为。与 `dsh-agent-instructions` 候选值冲突的 `conventionFileNames` 必须大声失败，而不是让一个目录产生两个归属方。

`budgetProfile` 除三个上限档位外也接受自适应模式，而 `budgetOverrides` 即使在自适应模式下也会被校验，因此一个错误的覆盖会在激活时失败，而不是等到第一次装配。

注入上限被刻意排除在这张表之外。它们恰好有一个归属方——预算档位——因此 `maxIdentityBytes` 及其同族无法获得第二个默认值。

### 信任梯度

| 层级 | 写入方 | 是否占有位置 |
|---|---|---|
| `auto` | 模型提议 | 否 |
| `confirmed` | 人工审批 | 是，若标题行能放下 |
| `curated` | 人工审批 | 是 |

模型只能写 `auto`。晋升经由 harness 的审批面，它复用已有的 `approval/asked` 与 `approval/decided` 事件，且只在结果为 `allowed-once` 时发生。在没有组合出审批面的地方，请求解析为 `unavailable`，事实保持未确认：注入是一项长期成本，因此绝不在没有人的情况下授予，而 fail closed 是正确行为，不是需要绕开的错误。

由于只有已确认的知识才会被带入新会话，永久注入的载荷恰好就是人工同意为之付费的那一集合。

### 打包与加载

插件以名为 `dsh-context-ledger` 的非作用域 ESM 包形式发布，是带 JSDoc 类型、无构建步骤的纯 ESM——也就是插件开发参考为 Host-only bundle 给出的形态。其入口导出 `name`、`inject`、`apply` 与 `Config`。

`inject` 只声明插件离开就无法工作的服务：`systemPrompt` 与 `tools`。文件系统 provider、token meter、模型路由与审批面都通过 `ctx.get` 读取，因此缺少其一的部署只失去对应能力，而不会加载失败；而一个声明了自己并不需要的服务的插件，会在缺少该服务的 profile 中处于非激活状态。

它在清单中声明 `dsh.bundle`，因此安装方式为 `dsh plugin --profile <name> add <spec>`，且 profile bundle 的接线由工具生成。不支持手写 loader 条目：重复的条目 id 会导致启动失败，这正是占用该名字的插件之一有文档记载的失败模式。可复现安装需要钉定 commit 或 tag。

由于插件只写入 `$DSH_HOME` 之下，以 `SandboxMode` `read-only` 运行的部署会失去记忆持久化并如实说明，而不是启动失败。它不会为读取而回退到 `node:fs`：绕过一个缺失的文件系统 provider 会在开发者机器上正常工作，同时静默绕过沙箱与任何远程文件系统。

### 实现状态

四个阶段全部收口：第 0 至第 3 阶段已构建并测试，第 4 阶段通过否决其指定的引擎、并交付该阶段真正需要的可观测性而关闭。

已构建：身份块、预算档位与自适应模式、文件承载的项目记忆、机械会话归档、触碰时投递的目录约定，以及七个面向模型的工具（`ledger_write`、`ledger_read`、`ledger_search`、`ledger_promote`、`ledger_status`、`ledger_history`、`ledger_handoff`）。196 个单元测试覆盖预算解析器与级别阶梯、条目模型及其存储格式、归档行及其存储格式、在真实临时目录上的存储、渲染器的逐字节稳定与让位顺序、简报的让位阶梯、约定候选解析与每文件一次的投递台账、各工具，以及包含捕获顺序、约定投递、"级别只在检查点移动而绝不在工具结果上移动"、以及"`ledger_status` 报告会话实际取用的级别"在内的插件接线。loader 侧验证显示模块可导入且全部十个 `Config` 字段被收集，无任何诊断。

通过读代码而非运行来验证的：上面那条保留机制，以及强制的 `compaction/*` 括号。两者都引用了确立它们的代码行。

在此处无法验证的：块真的到达了运行中的模型请求、已确认事实真的在实践上跨越压缩存活、逐字节稳定真的端到端抑制了快照抖动、简报真的帮到一个全新会话，以及被投递的约定真的在需要之前到达。这些都需要真实模型，而本检出没有可用的 key。归档推导同样只针对合成事件列表演练过，而非真实会话日志。

侦察改变的东西，除事件表之外还有：按会话的开关变成部署字段；上限变成字节；派生索引文件被放弃，改为扫描；基于摘要的缓存键被替换为比较渲染文本；注入上限从 `Config` 移进档位，从而只有一个归属方；自动接续与跨会话快照因找不到可达的接缝而被放弃；约定投递从 `agent/pre-step` waterfall 改为只用 inbox；老化被否决；全局作用域被推迟；替换压缩引擎被否决，改为让自适应模式变得可观测。

| 阶段 | 交付内容 | 退出标准 | 状态 |
|---|---|---|---|
| 0 | 第一层身份 | 在 git 检出目录中的新会话显示 `<project_context>` 块；在输入未变的步骤之间该块逐字节相同 | 完成 |
| 1 | 第三层项目记忆、四个记忆工具加 `ledger_status`、带显式解析的静态预算档位 | 一条已确认事实在压缩后仍然存在，并出现在后续会话中而无需重新读取旧记录；仅存在于无位置事实中的词项仍可通过 `ledger_search` 找到；无标记的目录不贡献任何内容 | 完成 |
| 2 | 第四层机械归档、`ledger_history`、`ledger_handoff` | 归档行是该会话事件的纯函数，且仅凭日志即可复现；捕获在读取之前先 flush，因此该行不会漏掉尾部；简报在其字节上限之内携带近期会话与注入事实 | 完成 |
| 3 | 第二层约定、带检查点切换的自适应模式 | 目录 `CONTEXT.md` 在触碰时投递、在此之前不投递，每个文件每会话一次，且最近的在前；超出单文件上限的约定被如实报告而非丢弃；级别只在检查点移动，绝不在工具结果上移动；窗口无法测量时回退到默认档位 | 完成 |
| 4 | 自适应可观测性；第 4 阶段原本指定的替换压缩引擎被否决 | 自适应部署能从 `ledger_status` 说明自己处在哪一级以及为什么；替换 `ctx.compaction` 的部署能在账本无需改动的情况下改变保留行为，因为它所折叠的 `compaction/*` 括号由平台强制 | 完成 |

第 4 阶段原本要求一个可选的替换压缩引擎。它被否决，理由见"考虑过的替代方案"；而它的退出标准其实是**本来就已满足**的：账本在替换引擎下无需任何改动，且它所依赖的 `compaction/*` 括号由压缩不变量与会话格式强制，而不是靠约定。这一阶段真正需要的工作恰恰不是新引擎——而是自适应模式**不可观测**，于是块缩到地板的部署除了一个空账本之外无物可看。那才是第 4 阶段交付的东西。

第 3 阶段原本还带有 `indexAgingSessions` 与全局作用域。老化被否决，全局作用域被推迟；两者都记录在"考虑过的替代方案"中，没有任何一项是无声缺失的。

第 2 阶段原本的退出标准——交接后的接续会话能够回答关于交接前工作的问题——是在假定插件能开启接续会话的前提下写下的。它做不到（见第四层），因此标准变成了上面那条：改为断言归档行与简报中可验证的性质，而不是一个需要真实模型、且需要一条并不存在的接缝的行为。

## 考虑过的替代方案

**自动开启接续会话并以简报作为种子。** 这是原本的设计，现已放弃，因为接缝不接受调用方给的种子。`ctx.subagents.startContinuable` 会创建新会话，但其种子来自 provider，因此简报无法放在它的开头；`ctx.agents.create({ seed })` 接受种子，但它是 agent-loop 工厂基础设施而非已发布的插件接缝，而且它的种子是原始事件前缀而不是简报；子 agent 也是被委派的任务而非主线程的延续。勉强组合这些原语，意味着依赖一条可能随时变化而无人预警的内部接缝。改为返回简报，而这一层的价值建立在一个事实之上：同一项目中的新会话已经会收到项目块与已确认事实。

**让归档存放模型撰写的摘要。** 否决原因是本插件的全部主张就是不与日志产生分歧。从会话推导出的摘要，是对一个已经存在之物所作的、更易失真的第二份叙述，而其失效模式是安静的：它偏离日志，而无人能判断哪一份才对。一行计数与名称不会偏离，而计数回答不了的东西有 `ledger_read` 与会话日志。

**在 `ctx.sessionReferenceResolver` 上构建跨会话快照。** 推迟，而非否决。该服务是构建另一个会话有界只读视图的受认可方式，且可从插件调用，但随附 bundle 不挂载它，因此这段代码在默认部署中不可达——与让 `session-stats` 不进入捕获路径是同一个理由。它属于挂载了该服务的部署。

**在 N 个未引用会话后让索引位置老化失效。** 这在原设计里，现已被否决。条目数与字节上限已经约束了常开载荷，因此老化无法让它更紧——它只决定哪些事实占住位置，而其效果是把一条极少触碰的事实换成一条最近触碰过的。那恰恰是本设计自己的风险清单点名过的伤害，而极少触碰的事实往往正是承重的那条：一个季度一次的发布流程极少被触碰，却正是必须始终在场的东西。保护这种事实的机制已经存在，而且比老化更强，因为它是刻意的动作而非计时器：把它晋升为 `curated` 就会凌驾于一切之上，且永远不会被新鲜度挤掉。老化本会添加第二个、更弱的杠杆，而其失效模式是静默移除。

**现在就为全局作用域开一条独立的注入路径。** 推迟，而非否决。一条全局事实会被注入到每个项目的每个会话，那是比任何项目事实都更大的长期税，而且由可能与它毫无关系的项目来支付。本设计赖以建立的克制原则——不赚取则不携带——在这个作用域上力度更大而非更小。加入它之前应先决定两件事：一条全局事实究竟该进入每个项目的块，还是只进入主动请求它的那些项目；以及用什么独立的上限约束它——因为让它与项目标题行争夺同一份预算，会让一条全局事实挤掉项目自己的知识。这些是值得明确回答的设计问题，不是可以默认假定的事。

**把约定投递经由 `agent/pre-step` waterfall 实现。** 实际用了另一种方式，waterfall 被放弃。`dsh-agent-instructions` 需要 waterfall，是因为它在调和指令集：它会改写一步将要纳入的消息，并在某一步开着时推迟变更。本插件只为下一步添加上下文，从不改写决策，因此那个 waterfall、它的 `next()` 委派义务，以及它的 step-open 簿记，都会是一套没有任何东西可决策的机器。inbox 记录了实际投递了什么，而两种方式下 Harness 都会记录这次拼接。

**交付一个可选的替换压缩引擎。** 否决，而接缝不是理由。替换 `ctx.compaction` 确实是被支持的：`packages/compaction/compaction/README.md` 记载了扩展其基类并作为插件加载，`docs/subsystems/compaction.md` 也把后端描述为"实现同一接口的兄弟包"。否决的理由是它**是另一个产品**。压缩引擎拥有摘要、区域选择、token 核算、检查点语义与并发锁；本插件必须把这一切重新实现一遍，才能改变一个它已经通过放置设计掉了的保留行为。一个核心主张是"在 DSH 中那场斗争是不必要的"的设计，不应随后就加入那场斗争。想要不同保留行为的部署可以自行取用那个接缝，而账本会在替换中继续工作，因为它唯一的耦合是 `compaction/*` 括号，而该括号的存在由平台强制。

**在每次压缩后注入一份块以重新宣告它。** 否决。它确实能补上那一次请求的间隙，但代价是每次压缩都追加一条新的持久消息、永远如此——用无界的日志增长换取一个有界、能自愈的一次请求间隙。inbox 是一次性投递通道，不是重新物化原语；把它当成后者，等于用更差的成本结构复制了快照机制。

**fork `P02-1010751281/dsh-project-context`。** 它是唯一一个功能列表与需求相符的现有实现。它在两个近期 dsh 版本上均未通过 L5 运行验证，因此第一项任务会是诊断启动失败，而不是构建能力。它的记忆模型还与 *Model-visible ⟺ logged* 相矛盾，而这正是整个设计赖以存在的属性。复用其架构意味着同时继承这两个问题。

**fork `buhuikongpan/dsh-project-context`。** 它能运行，且其机制——按步骤求值的动态上下文——是正确的基础，第一层正是复用了这一形态。它的代码库没有可扩展的记忆、归档或交接，因此把它留作基底，除了那个已被记载为一等公民扩展点的模式之外，什么也换不来。

**把项目记忆存放在项目目录树中并提交。** 这是早先的立场，现已放弃。提交机器写入的记忆，会把模型撰写的内容发布到共享仓库，让每个队友继承某一个用户的推断，同时给没人要求审阅的文件增加审阅负担。仅限本地让项目记忆成为按用户隔离的产物，也让删除具备明确含义：移除账本目录即彻底遗忘，完备且不留残余。其代价是被知情接受的：记忆不随仓库传播，队友也不会继承它。

**把记忆存进 `ctx.storageDomain` 而不是文件。** 域这种形式是受认可的插件自有存储，它会带来打开时的 schema 校验与写入时的变更事件。文件胜出，是因为正文是人预期要阅读和编辑的文字，也因为删除一个目录是彻底遗忘的完备且自明的方式——域没有同样显然的抹除手段。代价是插件要自己校验自己的记录，并自己负责原子性。

**以输入的摘要作为注入块的缓存键。** 最初就是这么构建的，后来被替换。摘要是渲染文本的代理，因此任何它漏掉的输入都会交出陈旧的块；当第 1 阶段把渲染器的输入从四个增加到八个，让两者保持同步本身就成了风险。比较渲染文本不可能与注入内容产生分歧，而渲染相对于插件无论如何都必须做的目录扫描而言，只是几次字符串拼接。

**把上限的单位定为 token。** 否决原因是插件没有分词器，任何字节到 token 的换算都会是把猜测当作测量来呈现。字节是精确的，而诚实的 token 数字——会话总量——已经可得，并在它该在的地方报告，且标明为会话级。

**让会话作用域的知识在证明有用后自动累积进项目作用域。** 否决原因是"有用"没有机械判据，且失败模式是静默的：永久注入的载荷会随模型运行量成比例增长，直到每个新会话一开始就背负着一个它并未选择的预算。要求由人工审批事件跨越这条边界，可以让这种增长成为一个决定，而不是一种漂移。

**提供一个完全没有上限的模式。** 否决原因是无上界的常开注入正是上限所要防范的失效，而其症状——提示词不断增长直到每个请求都又慢又贵——会在该设置被选定很久之后才显现。`full` 抬高上限同时让那个数字保持可检查，而真正想要无上界的部署应通过覆盖显式声明一个，使其在配置评审中可见，而不是由一个预设名来暗示。

**让模型自行选择预算。** 否决原因是模型正是预算所消耗的那个上下文的主体，而单个轮次内的信息无法区分"我需要更多记忆"与"更多记忆会更好"。档位由部署选择；而 `adaptive` 覆盖了正确答案随窗口填充而变化、却无人决策的情形。

**在仓库内构建为 `packages/context/project-context`。** 若插件被验证有效，这是最终归宿。它到首次演示更慢，因为它要接受完整的仓库内门槛——逐文件 100% 覆盖率、无密钥的录制会话快照、双语文档、JSDoc gate、重复检测。对于一个尚未验证的设计，这道门槛会在设计被证明值得之前先行支付。

**为模型可见面采用 Scroll 或 RationaleVault。** 它们贡献的能力——针对会话状态运行程序并只接纳其打印内容——在本地已作为 `dsh-ptc-runtime` 存在，其约定是针对宿主提供的绑定运行一个程序，并报告它打印和返回了什么。引入外部投影引擎会重复一个一等公民接缝，并扩大信任边界。

**为多图记忆采用 ContextDB 或 NeuSymMS。** DSH 没有对应物，因此这是真实的能力缺口，而非重复。它是被推迟而非被否决：一个基于有上限、已确认条目的机械存储，无需新的存储引擎、网络依赖，也不需要一项其成本不受字节上限管辖的检索开销，就能回答大多数接续问题。只有当中机械列表被实测证明不足之后，多图检索才值得其成本。

**只依赖 `AGENTS.md`。** 指令文件是一份由人编写的静态约定。它们无法记录会话学到了什么，也无法被模型写入，因为模型没有为此的持久词汇表——而条目存储正是那套词汇表。

**把插件命名为 `dsh-project-context`。** 否决原因是两个互不兼容的社区插件已经占用了该名字，而其中一个有文档记载的安装路径在存在第二个同 id 的 loader 条目时会启动失败。一个独特的名字可以让 loader 条目 id 与失败模式都不产生歧义。

## 验收标准

在项目目录中的会话显示一个由解析出的项目根推导出的 `<project_context>` 块，且重放该会话日志时同一块被复现。

不带标记的目录不贡献任何内容；没有工作目录的会话、以及没有文件系统 provider 的部署同样如此。

在输入未变的相邻步骤之间块逐字节相同，且渲染是其输入的确定性函数——直接针对渲染器断言。

在所有层都启用时，解析出的上限被执行并被报告：`ledger_status` 返回当前档位与恰好生效的上限，且 `budgetOverrides` 优先于档位。

添加事实永远不会让每请求成本超出上限：一旦条目数或标题行字节上限被触及，后续事实就拿不到位置，块也不再增长。

目录行报告的是屏幕上显示的内容而非仅仅具备资格的内容，并且它会针对实际渲染出的内容重新计算。

没有位置的事实仍然可被获取：对于它所包含的词项，`ledger_search` 会在工具结果上限之内返回它。

内容按固定顺序让位——标题行、目录行、技术栈行、项目名——若连根行都放不下，则什么也不贡献。任何值都不会被中途截断。

任何时刻都不在项目目录树之下写入文件；在一整段会话中项目内的 `git status` 保持干净。

模型写入的事实以 `auto` 存储，且绝不出现在块中。晋升只在 `allowed-once` 审批下发生；在没有审批面的地方，该尝试报告 `unavailable` 且层级不变。

重写一条已确认事实会保留其层级，因此一次编辑无法静默降级人的决定。

删除账本目录会移除全部记忆：后续会话不显示任何事实、报告零记录，且不产生错误。

格式错误或不可读的条目文件会被连原因一起报告并跳过，绝不让一次列表或一个会话失败。

会逃出记忆目录的 id 在拼接到路径之前即被拒绝。

配置表中的每一项阈值都可在 `cordis.yml` 中更改并在加载时校验；未知档位、未知覆盖键或不可用的值会让激活失败，而不是静默改变行为。

当 `SandboxMode` 设为 `read-only` 时，插件正常加载并贡献该块，而不是启动失败。

安装第二个声明了相同名字的插件，或手写重复的 loader 条目，会在加载时大声失败，并给出指出冲突的消息。

归档行是会话事件的纯函数，直接针对推导器断言；没有事件的会话不归档任何内容。

捕获在读取之前先 flush 会话，针对调用顺序断言，因此一行不会悄悄漏掉日志尾部。

捕获失败会被记录，绝不以拆除错误的形式浮现，也不会留下半行。

任何项目之外的会话都不被归档；在 `archiveEnabled` 为 false 时不归档任何内容，而块仍然照常贡献。

重新归档一个被恢复的会话会替换其行而非新增一行，因为后一行覆盖了更长的日志。

格式错误或不可读的归档文件会被连原因一起报告并跳过，绝不让一次列表失败。

简报在其字节上限之内携带近期会话与注入事实，按文档顺序让位——事实、路径列表、除最近一条之外的所有行、然后是所有行——且绝不中途截断任何值。

约定只在其目录被触碰之后投递、绝不在之前，且每个文件每会话只投递一次；候选从被触碰文件所在目录向上到项目根、最近的在前，而项目之外的文件没有任何候选。

超出单文件上限的约定会在投递的消息中被如实报告而非丢弃；无法放进会话上限的约定则什么也不贡献，而不是贡献一个片段。

约定读取失败会被容纳并记录，且插件绝不会把它变成工具失败。

自适应级别是其整块上限能放进空闲窗口配置比例的最宽一档，跨窗口尺寸断言；没有余量的窗口得到仅身份地板；而无法测量的窗口回退到默认档位而不是猜测。

自适应级别只在检查点移动——会话开始、轮次边界、或一次压缩结束——绝不在工具结果上移动；通过释放窗口并观察"工具结果不使块变宽、而轮次边界使之变宽"来断言。

上限覆盖值为零会被接受并意为"无"，因此部署可以在不换档位的情况下关掉某条路径，而仅身份地板无需在渲染器里特判即可表达。

`ledger_status` 报告配置的档位、当前级别、比例，以及选择该级别的测量；既针对桩断言，也经由真实接线断言，因此块缩小的自适应部署能看到原因，而不是面对一个无从解释的空账本。

尚未测量过级别的会话会如实报告这一点，而不是把默认档位报成已测量；静态档位也如实自报为静态，而不是编造一次测量。

## 风险

**简报不是交接。** 没有任何东西把它带到任何地方：模型必须选择产出一份，而继续工作的人必须据此行动。一份被生成又被无视的简报只花掉一次工具调用，什么也没改变。缓解在于简报以"开一个新会话"的指令收尾，而且即使简报被丢弃，新会话仍然有用——它会照常收到项目块与已确认事实。

**归档在失败时按设计保持沉默。** 捕获发生在销毁的 emit 上，因此没有东西等待它，也没有东西把它的失败报告给不看日志的人。期望有归档的部署应当去查 `ledger_history`，而不是假定它存在。这个取舍是正确的——归档不值得换来一个拆除错误——但它意味着归档的缺失与一个没有历史的项目无法区分。

**压缩之后可能有一次请求拿不到块。** `project()` 运行在压力压缩所在的 pre-step waterfall 之前，因此压缩移除该快照的那一步会省略它，而溢出恢复可能让重试的那一次请求漏掉它。下一次装配会恢复它，所以这是间隙而非丢失——但在这期间作答的模型是在没有项目块的情况下作答的，而没有任何东西报告此事发生过。用"每次压缩后注入一份新副本"来补上它已被否决，因为那是用无界日志增长换一个有界间隙。

**仅限本地的记忆不会传播，也无法恢复。** 克隆仓库的队友不会继承任何记忆，丢失机器即丢失账本。这是"仅限本地"决定所接受的代价，它使入职与备份成为用户自己的事情，而不是插件能解决的问题。

**插件状态不再随其会话重放。** 放弃事件设计确实损失了一项真实性质：启用标志、预算选择，以及每个条目的历史，都是宿主侧状态，会话导出不会携带。导出与重放展示的是*效果*——块当时的样子，因为它是一条被记录的消息——而不是产生它的插件状态。要恢复该标志，需要一个面向第三方 ignorable 事件的上游接缝，而它并不存在。

**上限以字节执行，而成本以 token 支付。** 字节精确地约束了插件自身的贡献，但一个标题行的字节数与 token 数并非同一个数字，因此在一个以 token 计便宜、以字节计密集的脚本中，项目可能比所报告的数字更接近 token 预算。缓解在于这些数字相对于上下文窗口很小；风险在于它们被当作 token 保证来对待。

**上限仍然在不询问模型的情况下决定它看到什么。** 档位把这个决定移交给部署，目录行让省略变得可见，但两者都不会让模型去检索。从不调用 `ledger_search` 的模型受当前档位约束，其残余代价是一个本可借助账本所持事实的任务在缺少该事实的情况下继续推进。对策是度量：记录一次会话的答案依赖无位置事实的频率，并让该数字——而不是上限——成为放宽档位的依据。

**位置由信任与新鲜度占据，而新鲜度仍然可能是错的。** 老化被否决（见"考虑过的替代方案"）之后，一条极少触碰但承重的事实只能靠被晋升为 `curated` 来保护。没有任何东西强制项目这么做，也没有任何东西在一条 `confirmed` 事实因更新的事实涌入而掉出块时发出警告。`ledger_status` 报告有多少事实仅可检索，因此问题的形状是可见的，但唯一的杠杆是人决定去晋升。

**缺少全局作用域，而这种缺失会被感觉到。** 一条关于机器或人而非项目的事实——这次检出需要哪个测试参数、他们偏好哪个包管理器——没有归宿，于是要么在每个项目里重复记录，要么丢失。推迟是刻意的，理由在"考虑过的替代方案"中，但这意味着本插件的知识在构造上就是按项目隔离的。

**一条值得确认的事实可能永远不会被提议。** 信任梯度依赖模型主动提出晋升它所记录的内容，并依赖有人在场批准。在无人值守的部署中，什么都永远不会被确认，块因此保持为空，插件的价值退化为仅有身份。这是设计上的 fail closed，但失效是安静的。

**注入的上下文可能在会话内过期。** 快照机制使变化在下一次装配时可见，但被工具调用在同一轮次内修改过的项目，到那时之前仍由上一个快照描述。在每个工具结果上重新解析被否决，因为其成本超过新鲜度本身的价值。父 agent 也只能在其下一个轮次边界才会跟上子 agent 的写入。

**渐进式披露可能投递不足。** 从未被触碰的约定文件永远不会被注入，这正是意图所在；但若任务在触碰其目录之前就需要某个约定，它就会拿到得太晚。投递现在已运行，剩下的问题是度量：记录一次约定在需要之后才到达的频率，然后才能把投递规则视为已定。

**约定的一次性成本仍然可能被反复支付。** 每个文件在每个会话中只投递一次，但一个触碰了许多目录的长会话会为每一个都付费，而一个每个目录都有 `CONTEXT.md` 的项目会在一生中为全部付费。会话字节上限约束的是文本总量；没有任何东西约束注入的次数。

**落地依赖于插件先能运行。** 需求明确要求独立插件，因此它必须能在已安装的 dsh 上运行而不修改源码。如果某个所需扩展点在仓库内存在、却无法从安装进 profile 的插件触达，该缺口会阻塞对应层级，而不能就地修复；它必须作为发现上报，而不是通过 fork DSH 来绕过。

**被推迟的多图检索可能最终是承重的。** 如果带上限的机械列表在真实项目规模下被证明不足，上文替代方案中的推迟就会转化为一项带外部依赖的计划外工作，而该依赖的检索成本不受字节上限管辖。第二阶段的退出标准正是此事的可度量时点。
